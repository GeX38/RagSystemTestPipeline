# RagSystemTestPipeline

Языки: [EN](./README.md) | [RU](./README.ru.md)

RagSystemTestPipeline - автономный репозиторий для воспроизводимой оценки
качества медицинских ИИ-помощников по траекториям диалога. Он не содержит сам
медицинский ассистент или RAG-систему. Его задача: дать независимый пайплайн,
который можно подключить к результатам любой системы и получить сопоставимую
оценку клинической логики, безопасности и прозрачности ответа.

## Для чего это нужно

Пайплайн помогает проверить, как медицинский ИИ-помощник ведет себя в
многошаговом клиническом сценарии:

- удерживает и пересматривает диагностические гипотезы по мере раскрытия данных;
- замечает красные флаги и выбирает безопасную маршрутизацию;
- не предлагает самопомощь там, где нужен срочный очный контакт с врачом;
- задает релевантные уточняющие вопросы;
- объясняет выводы и не добавляет факты, которых не было в кейсе.

## Что входит

- Переносимый модуль полной методики:
  [`methodology_full_test_portable/`](./methodology_full_test_portable/).
- Набор критериев и порогов:
  [`clinical_methodology_metrics.json`](./methodology_full_test_portable/clinical_methodology_metrics.json).
- Пример входного кейса:
  [`input.example.json`](./methodology_full_test_portable/input.example.json).
- Prompt-логика для judge-модели и детерминированный расчет итоговых баллов.

## Что не входит

- RAG-пайплайн оцениваемого ассистента.
- Retrieval, embeddings, векторная база или хранилище диалогов.
- UI, админ-панель, веб-сервис или деплой.
- Реализация конкретного LLM-провайдера.

Такой состав сделан намеренно: оценочный пайплайн должен быть отделен от
оцениваемой системы и от выбранной judge-модели.

## Методика в двух словах

На вход подаются:

- `case`: клинический кейс, экспертный эталон, критические признаки и красные флаги;
- `trajectory`: многошаговая история взаимодействия пользователя и ассистента.

Пайплайн отдельно оценивает:

- blocking-критерии клинической безопасности;
- домены диагностической точности, логической последовательности, безопасности,
  качества информационного поиска, прозрачности и достоверности.

На выходе формируется итоговая оценка:

- `okl_score`: интегральный балл по доменам;
- `judge_class`: класс `A`, `B` или `C`;
- `blocking_failed`: флаг провала критического safety-критерия;
- расшифровка оценок по каждому критерию.

Если хотя бы один blocking-критерий не выполнен, результат автоматически
переходит в класс `C`, даже при высоких доменных баллах.

## Быстрый старт

1. Откройте пример входных данных:
   [`methodology_full_test_portable/input.example.json`](./methodology_full_test_portable/input.example.json).
2. Подготовьте траекторию ответов вашего медицинского ассистента в таком же формате.
3. Подключите judge-модель через объект `judge_client`.
4. Запустите `run_full_methodology_test(...)` из переносимого модуля.

Подробный технический контракт описан здесь:

- [документация модуля на русском](./methodology_full_test_portable/README.ru.md);
- [module documentation in English](./methodology_full_test_portable/README.md).

## Рекомендуемый сценарий использования

1. Зафиксировать набор клинических кейсов и экспертных эталонов.
2. Прогнать один или несколько ассистентов по одинаковым staged-disclosure траекториям.
3. Сохранить ответы ассистентов в формате `trajectory`.
4. Запустить оценку одной и той же judge-моделью с одинаковыми параметрами.
5. Сравнить `judge_class`, `okl_score`, blocking-критерии и доменные профили.

## Ограничения

- Методика оценивает поведение ИИ-системы, а не ставит диагноз пациенту.
- Качество результата зависит от выбранной judge-модели и стабильности ее JSON-ответов.
- Для сопоставимых прогонов используйте одинаковые кейсы, критерии, judge-модель
  и параметры генерации.
- Для рабочих сравнений рекомендуется низкая температура judge-модели, например
  `judge_temperature <= 0.15`.
